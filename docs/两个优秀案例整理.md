# 两个优秀案例整理与本项目实施启发

## 阅读范围与结论

根据课程 `samples/sample.zip`，选择**线上教学系统**与 **LOCUS 房产平台**两个案例进行整理。这里“优秀”指值得学习的设计与实现，不代表已核实的教师评分或正式评奖。

本次依据项目报告、架构说明、路由及关键业务代码做静态分析；没有启动服务、实际操作页面或验证外部 API，故“报告描述的功能”“代码中观察到的实现”与“本项目建议”分别表述。

最值得本项目借鉴的是：清晰的角色、能够走通的业务流程、真实持久化、可追踪的前后端接口，以及按业务区域组织页面。复杂基础设施和大量功能不应直接成为本次作业范围。

## 案例一：线上教学系统

### 1. 软件定位与用户

面向教师与学生，把课程、通知、作业、考试、问卷和聊天组织在同一教学系统中。

| 用户 | 核心任务 |
| --- | --- |
| 教师 | 创建课程、发布任务、管理成员、批改并反馈 |
| 学生 | 进入课程、阅读通知、提交作业、填写问卷、查看反馈 |

### 2. 原案例的功能范围

依据案例 `report.md`：

- 账号：登录、注册及个人资料维护。
- 课程：创建、加入、退出、删除，查看成员变动。
- 通知：发布与阅读课程公告。
- 作业：布置、提交、批改、成绩与反馈。
- 考试：导入答卷、分配批改、成绩发布，以及仲裁和申诉。
- 问卷：设计、填写、查看结果与选项统计。
- 聊天与附件：课程聊天、撤回或隐藏消息，部分业务支持附件。
- 工作台：汇总通知及待办，提供进入业务的入口。

以上是原报告的功能陈述，不能替代运行验收。代码已核实存在课程工作区、作业创建及多类业务路由。

### 3. 页面如何围绕业务组织

`frontend/src/router.tsx` 中可见登录、注册、个人信息、首页、课程工作区、公告、作业、批改、考试和问卷等页面。原案例规模明显超过约 10 页，不宜完整复制。

`pages/courseWorkspace/index.tsx` 主要执行状态判断，并组合 `CourseWorkspaceHeader` 和 `CourseWorkspacePanel`；页面状态由 `useCourseWorkspacePage` 提供，入口没有直接塞入全部业务实现。

值得学习的是“课程作为业务上下文”：用户选中课程后，在该课程下处理通知、作业等任务。不要让每个功能都成为互不关联的独立页面。

### 4. 已核实的后端流程

`CreateAssignmentAPIMessage.scala` 的创建作业流程可以概括为：

```text
查询课程、操作人及批改人
  → 校验操作人是当前课程教师
  → 校验批改人、标题、内容、分值和时间
  → 生成规范化的作业对象
  → 在事务连接中写入
  → 返回更新后的课程详情
```

代码同时使用 `IO` 与 `Either` 表达效果和校验结果。它体现了“先校验业务条件，再写入并返回可展示结果”的流程。

不能据此断言整个系统没有权限问题：该文件如何取得可信操作人，还需要继续核验上游身份边界。

### 5. 架构与值得学习的地方

后端 README 说明技术栈为 Scala 3、Cats Effect IO、http4s、Circe、PostgreSQL 和 HikariCP，并组织教学领域模块。项目报告列出 auth、assignment、course、dashboard、exam、questionnaire；后端 README 还列出了 asset 等内容，说明不同文档的模块口径并不完全相同。

| 值得学习 | 对本项目的意义 |
| --- | --- |
| 教师与学生职责不同 | 页面可见性和后端授权规则应同时设计 |
| 发布、提交、批改、反馈形成闭环 | 演示要展示前后操作的联系，而非逐页浏览 |
| 业务对象有明确联系 | 数据模型先确定用户、课程、作业、提交、评价等关系 |
| 工作台汇总真实待办 | 首页展示由业务数据生成的概况，减少装饰性空卡片 |
| 页面入口与状态 Hook 分开 | 界面结构、状态协调和纯计算各有位置 |

### 6. 不能直接照搬的地方

- 原案例包含 Kafka、Redis、MinIO 等基础设施；本次约 10 页作业不必全部引入。
- 仲裁、申诉、考试批改等功能复杂，容易挤占主要流程的实现与测试时间。
- 该案例消息方法是 `def plan: IO[...]`，并非本项目要求的 `plan(connection: Connection)`；借鉴业务结构时须按本项目规章调整。
- 案例中存在 `microservices`、`support`、`shared` 等组织方式，与 `rules.txt` 的具体目录约定不同，不能直接视为规则豁免。

### 7. 如果选择教学主题，建议精简为 10 页

以下是本项目候选方案，不是原案例页面的逐项复制，也不是已确定选题：

| 页码 | 页面 | 主要职责 |
| --- | --- | --- |
| 1 | 登录 | 识别用户与角色 |
| 2 | 注册 | 创建演示所需账号 |
| 3 | 我的课程 / 工作台 | 课程入口与待办概况 |
| 4 | 课程详情 | 公告摘要、任务与成员入口 |
| 5 | 课程创建与编辑 | 教师维护课程 |
| 6 | 课程成员管理 | 管理成员及角色范围 |
| 7 | 作业创建与编辑 | 教师发布任务和截止时间 |
| 8 | 作业详情与提交 | 学生查看要求并提交 |
| 9 | 批改管理 | 教师查看提交并给出评价 |
| 10 | 我的成绩与反馈 | 学生查看处理结果 |

主演示流程：教师发布作业 → 学生提交 → 教师批改 → 学生查看反馈。公告可先作为课程详情区块；暂不纳入考试、问卷、即时聊天与大型附件系统。

## 案例二：LOCUS 房产平台

### 1. 软件定位与用户

面向买家、租客和房产经纪人，连接房源发布、搜索浏览、收藏、咨询和看房预约。

| 用户 | 核心任务 |
| --- | --- |
| 买家 / 租客 | 查找房源、查看详情、收藏、咨询、预约看房 |
| 经纪人 | 发布和管理房源、维护看房时段、处理沟通、查看数据 |

### 2. 原案例的功能范围

依据 10 页 PDF 报告、前后端 README 与 `ARCHITECTURE.md`：

- 搜索：位置、价格、房型及其他条件筛选。
- 详情：图片、房屋信息、经纪人、收藏及业务入口。
- 房源管理：新建、编辑、预览、归档和图片维护。
- 收藏、实时消息与附件。
- 经纪人设置看房时段，买家预约、取消或调整预约。
- 地图、周边设施与街景。
- 户型分析及 AI 装修预览。
- 浏览、收藏、消息、预约等行为的统计分析。

地图、AI 和实时通信是报告描述的扩展能力，尚未在本机运行验证。

### 3. 页面与复杂区域的组织

路由代码中可见首页、房源列表、详情、收藏、消息、登录、注册、经纪人房源、编辑、预约管理和统计等页面。新建与编辑复用编辑页，预览复用详情页，不能把每个路由都等同于独立页面组件。

已检查的两个页面：

- `ListingDetailPage/index.tsx`：调用页面 Hook，处理加载或错误，组合侧边区段导航与详情区域。
- `AgentListingAnalyticsPage/index.tsx`：明确组合指标卡、趋势图、漏斗、来源分布、比较和近期活动等区域。

值得学习的是：复杂页面按可见业务区拆分，并把格式化函数与状态 Hook 分开；不是为了文件数量而拆分。

### 4. 已核实的预约流程

`BookInspectionSlotApiMessage.scala` 声明读写事务，通过可信 principal 取得用户，生成预约 ID 和时间，调用表方法；没有插入记录时返回冲突结果。

```text
请求预约时段
  → 以已认证用户作为预约人
  → 在写事务中尝试登记
  → 成功则返回预约后的时段信息
  → 时段不可用则返回冲突
```

`InspectionBookingsTable.scala` 中可见：预约表对 `slot_id` 有唯一约束；插入 SQL 检查时段尚未开始，且当前没有预约。这提供了真实的数据一致性约束。

仍需补验并发错误处理：`not exists` 不能单独保证并发安全，唯一约束可能触发数据库异常，必须核实这些异常是否正确转换为业务冲突。不能仅凭顺序执行代码就声称并发测试通过。

### 5. 架构与值得学习的地方

架构文档明确称其为**模块化单体**：一个后端应用、共享连接层，按 identity、listings、media、favourites、inspections、messaging 等领域组织。不是每个目录都单独部署为微服务。

| 值得学习 | 对本项目的意义 |
| --- | --- |
| 发布方与使用方共享同一份真实业务数据 | 创建后必须在另一角色的页面看到结果 |
| 消息接口与前端调用可追踪 | 每个按钮操作应能定位到消息、表操作和返回类型 |
| 预约具有时间和唯一性约束 | 业务规则不能只靠前端禁用按钮 |
| 统计与业务事件相连 | 图表应来源于真实记录，避免静态演示数字 |
| 模块化单体 | 在保持归属清晰的同时降低部署复杂度 |
| 图片元数据和文件内容分开 | 若确需上传功能，应明确文件和数据库各自职责 |

### 6. 不能直接照搬的地方

- Google Maps 与 AI 依赖外部配置、网络和可能的费用，不列为本项目默认必做功能。
- WebSocket、附件和图片生成会增加调试与提交包管理成本，须有实际业务价值才加入。
- 原项目使用带 Request 类型和 principal 的消息模型，与本项目单返回类型、构造参数和 `plan(connection)` 约定不同；采用思路而非复制基类。
- 原案例部分表对象采用服务私有可见性，且初始化与表操作同文件；本项目仍按既定公开 Table 边界和独立初始化文件执行。
- 报告中的完整体验、质量评价不能等同于我们已验证的事实。

### 7. 如果选择信息发布与预约主题，建议精简为 10 页

可沿用房源主题，也可将对象替换为活动、场地或其他待预约资源；改题材时必须同步调整业务规则。

| 页码 | 页面 | 主要职责 |
| --- | --- | --- |
| 1 | 登录 | 识别使用方 / 发布方 |
| 2 | 注册 | 创建账号 |
| 3 | 首页 | 搜索入口与最新资源 |
| 4 | 资源列表 | 筛选与分页 |
| 5 | 资源详情 | 内容、收藏、可预约时段 |
| 6 | 我的收藏 | 管理关注的资源 |
| 7 | 我的预约 | 查看或取消本人预约 |
| 8 | 发布管理 | 查看自己的资源并管理状态 |
| 9 | 资源新建与编辑 | 保存资源及基本信息 |
| 10 | 时段与预约管理 | 发布方设置时段并查看预约 |

主演示流程：发布方创建资源与时段 → 用户搜索 → 查看详情并预约 → 发布方查看预约 → 用户查看或取消。暂不加入付费 AI、地图、实时聊天及复杂分析面板。

## 两个案例给本项目的共同要求

| 优先级 | 我需要做的工作 | 验收证据 |
| --- | --- | --- |
| P_0 | 选定一个主题，明确两类角色及一条完整流程 | 角色权限表、流程说明 |
| P_0 | 完成约 10 个有实际用途的页面 | 页面清单与真实跳转 |
| P_0 | 实现前端、后端和数据库连接 | 创建后可查询，刷新或重启后仍保留 |
| P_0 | 后端校验身份、归属和关键业务约束 | 非法操作被拒绝，不能靠改请求绕过 |
| P_0 | 按本项目规范组织消息计划与效果边界 | `plan(connection)`、IO 组合、公开 Table 方法 |
| P_1 | 先交付一个纵向完整流程，再补其余页面 | 早期即可端到端演示 |
| P_1 | 页面入口、状态 Hook、纯函数和组件各有职责 | 打开入口即可辨认主要区域 |
| P_1 | 提供错误、加载、空数据和成功反馈 | 对应状态可实际触发 |
| P_1 | 提供初始化、配置模板、运行说明和必要测试 | 干净环境可复现，检查结果如实记录 |
| P_2 | 根据主流程选择一个有价值的特色 | 特色能参与业务，而非孤立展示 |

交付仍须满足截图要求：使用录像不超过 3 分钟、完整源码、附件不超过 100M。两个案例的精简页面表是候选方案，尚未替用户确定最终题目。
