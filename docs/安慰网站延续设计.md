# 安慰网站延续设计

## 1. 已确定的方向

用户明确要求本次项目延续之前的安慰网站。此前校园活动、设备借用、学习互评等选题建议不再作为本项目方向。

产品延续旧网站的“开灯与关灯”叙事；工程架构继续模仿教学系统与 LOCUS 的领域模块、消息式 API、页面 Hook 和业务组件组织。

**已确定的是主题与继承方向。下文新增页面、功能、模块与文案均为设计讨论稿，尚未逐项确认。**

## 2. 从旧项目继承什么

已读取原聊天《制作动态视频背景网页》及本地《安慰网站_需求与交接说明.md》，并确认恢复页面和源码包存在。

核心表达：每个人有两双眼睛，一双看清世俗的琐碎，另一双看透内心的美好。

| 继承内容 | 本次设计中的作用 |
| --- | --- |
| 开灯 / 关灯交互 | 首页的主体验与全站叙事起点 |
| 左侧人物场景，右侧文字和开关 | 延续已有构图，不直接改成普通管理后台 |
| 成年人物、自然立体、克制的光影 | 继续采用成熟、安静的视觉表达 |
| 人物写字、关灯、伏桌休息 | 让“停下来”成为体验的一部分 |
| 地面三个纸团与轻盈鸟影 | 表达琐碎之中仍有美好，保留原有羽翼细节 |
| 鸟向左侧窗外飞，纸团保持原位 | 延续已有的具体叙事约束 |
| 细丝、缓慢振翅、晚些出现的字幕 | 保留节奏，避免文案更新重启动画 |

旧项目选择的是 **v15 恢复版**，不是后来的 comfort-rebuild。它是使用当时素材恢复的版本，不等于完整历史快照；已有动作和视觉目标也不能当作全部已验收。

本次只读取旧项目资料，没有改动原文件，没有重新生成素材，也没有调用付费模型。正式接入时先保留原件，再在本项目副本中迁移和实播核验。

## 3. 从“一个安慰封面”扩展为“可以持续使用的安慰空间”

建议主流程：

```text
进入旧场景，体验开关灯
  → 选择现在的感受，或直接进入休息空间
  → 写下想说的话
  → 收到与所选主题匹配的安慰内容
  → 收藏或保存这次记录
  → 下次回来查看自己的片段
```

不要求每个用户都完成全部步骤；可以只看场景、读一句话或休息一下。账号主要用于保存和回顾，不应成为首页体验的门槛。

首版安慰内容建议来自经过人工整理的内容库，按用户主动选择的主题匹配。智能生成可以以后单独讨论，不默认接入聊天模型，不把安慰体验表述为诊断或治疗。

## 4. 约 10 页候选结构

| 页面 | 内容与作用 | 后端价值 |
| --- | --- | --- |
| 1. 首页：两双眼睛 | 原有开关灯场景、字幕、进入安慰空间 | 可读取公开场景文案；动画本身在前端运行 |
| 2. 登录与注册 | 同一账号入口切换登录 / 注册 | 创建账号、会话与身份校验 |
| 3. 此刻心情 | 主动选感受、强度和简短文字，可跳过 | 保存本人的心情记录 |
| 4. 写一封信 | 写给现在或未来的自己 | 草稿、保存、编辑 |
| 5. 我的信箱 | 查看自己的信，按时间或主题筛选 | 私有列表、分页查询 |
| 6. 信件详情与回应 | 阅读信件，呈现匹配的安慰卡片 | 本人权限、读取与更新、内容匹配 |
| 7. 安静片刻 | 呼吸节奏或短时休息，与原场景呼应 | 首版可以仅前端实现，不为每页强造 API |
| 8. 收藏的微光 | 保存喜欢的安慰句与卡片 | 收藏、取消收藏、个人列表 |
| 9. 来时的路 | 时间线与简单心情回顾 | 聚合本人的真实记录，不评价或排名 |
| 10. 我的空间 | 昵称、声音与动效偏好、个人数据管理 | 保存设置、删除自己的记录 |

页面名称为候选，不是最终文案。首页不强制登录；是否保存访客草稿、是否提供自动保存及声音素材，需继续讨论。

首版的信件和心情均为本人私有，不默认建设匿名树洞、陌生人私信或公开广场。若以后需要分享，应另行设计可见范围、举报与内容管理，而不是直接沿用私有记录。

## 5. 两个案例的架构如何用在这里

| 案例思想 | 安慰网站的对应实现 |
| --- | --- |
| 教学系统的提交与反馈闭环 | 写信 → 保存 → 获取安慰回应 → 回顾 |
| LOCUS 的详情页业务分区 | 信件详情由信件区、回应区、收藏操作区组成 |
| 两者的页面级 Hook | 协调草稿、请求、加载和操作状态 |
| 两者的领域模块 | 账号、心情、信件、安慰内容、个人回顾各有归属 |
| LOCUS 的真实数据驱动 | 信箱、收藏与时间线来自实际保存的数据 |
| 消息式 API 与 IO | 每个保存、读取、收藏操作能追踪到后端消息和表方法 |

原场景的动画控制与用户数据状态分开：保存草稿、刷新安慰句或收藏不能导致鸟影重新起飞。场景可用明确状态表达开灯、关灯过渡、夜间保持和返回过程，实际视频播放与 DOM 操作放在边界。

## 6. 后端模块候选

| 模块 | 职责与对象示例 |
| --- | --- |
| identity | User、Session，可信身份与用户设置 |
| mood | MoodEntry、FeelingTag，心情记录 |
| letters | Letter、LetterStatus，草稿和已保存信件 |
| comfort | ComfortCard、ComfortTopic、Favourite，内容匹配与收藏 |
| journey | 从信件和心情聚合个人回顾；复杂度低时可先不用独立模块 |
| system | 配置、连接、事务、路由和错误处理 |

采用一个 Scala 后端与 PostgreSQL 的模块化单体。接口遵循本项目 `final case class XxxMessage(...)`、`plan(connection): IO[Response]` 约定；页面遵循 React + TypeScript、Hook、纯函数及 Tailwind 约定。

安慰内容匹配可写为纯函数：根据显式输入的主题和候选内容返回卡片。数据库读取、当前时间与生成 ID 等在 IO 边界取得。若增加随机选句，随机来源同样放在边界，不能伪称纯函数。

## 7. 核心隐私与交互要求

- 心情、信件和回顾默认只允许本人访问，所有按 ID 读取、修改和删除均校验归属。
- 日志不记录信件正文、心情原文和会话凭据；GitHub 只保存合成演示数据。
- 收藏具有用户归属与去重约束；保存操作处理重复点击和失败反馈。
- 长动画可跳过，动效偏好可调整，声音不强制自动播放。
- 不用连续签到、心情排名或带责备意味的提示制造额外压力。

这些是为产品设计提出的工程与交互约束，不是对旧项目已实现功能的描述。

## 8. 第一条要实现的完整流程

1. 在 React 中接入旧场景的副本，保持素材和叙事顺序。
2. 用户登录后写一封信，保存到后端和数据库。
3. 信箱可查看该信，刷新后仍存在。
4. 按用户主动选择的主题展示一张安慰卡片。
5. 收藏卡片，在“收藏的微光”中能看到。

先把这一流程做通，再补心情回顾、设置及其余页面。不能只把静态封面拆成 10 页而没有真实后端功能。

## 9. 演示与接下来要讨论的内容

录像可依次展示：开关灯场景 → 记录此刻感受 → 写信并保存 → 查看回应并收藏 → 回到信箱与时间线。总时长按本次作业控制在 3 分钟内；不沿用第一次作业的 30 秒限制。

接下来重点讨论：

1. 你希望最核心的是“写信被安慰”，还是“进入场景安静休息”？
2. 原来的主角和房间是否只用于首页，还是贯穿信件和回顾页面？
3. 安慰回应先采用精选内容库，还是明确需要 AI 对话？

在答案明确前，不把候选功能当作最终需求，不重新生成鸟或替换原有视觉，不开始付费 API 调用。
