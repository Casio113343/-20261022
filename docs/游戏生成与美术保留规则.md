# 游戏生成与美术保留规则

- 日期：2026-10-31。
- 状态：用户已明确的产品要求，作为后续实现及验收依据。
- 适用范围：网站每次制作游戏及对已生成游戏的修改。
- 本文是项目需求，不是课程原文；不表示下述能力已经实现。

## 1. 核心要求

本产品是制作游戏的网站。用户发起一次新的游戏制作请求后，网站必须根据该游戏的玩法、世界观、人物及视觉要求，完成所需美术的生成与加工，并将这些素材用于实际可玩的图形游戏。

“生成美术”是每款游戏制作流程的一部分。开发时预先生成一套示例图、仅提供图片需求清单、让用户自行寻找图片，均不能替代网站对本次游戏执行的美术生成流程。

修改已有游戏时，默认继续使用现有美术。除用户明确提及的视觉改动，以及实现该改动确实需要的局部配套加工外，其余美术应尽量保持不变。普通游戏修改不能触发全套素材重画。

## 2. 新游戏的制作流程

沿用需求规格中的方案审阅和确认：用户确认方案并发起制作后，网站执行以下流程。

1. 读取本次已确认的玩法、世界观、人物、图片参考与视觉要求。
2. 按该玩法列出实际需要的美术，例如角色、场景、卡面、防御塔、敌人或道具；不要求每类游戏都生成所有种类。
3. 为本次游戏建立一致的美术风格，并生成相应素材。
4. 按运行需要加工素材，例如裁切、尺寸适配、透明背景处理、角色或动画帧整理、卡面合成及纹理导出。
5. 将成品绑定到游戏中的实际角色、场景、卡牌或其他对象，完成加载与运行验证。
6. 交付可玩的图形游戏，并保留与该游戏版本对应的素材记录。

角色名称、性格、身份、能力、世界设定、视觉要求和参考图应成为素材设计依据。不得把不同用户、不同游戏的请求统一替换成同一套演示图片，并声称完成了按需生成。用户明确要求沿用已有风格、人物或素材时，可按其要求复用。

加工应服务于游戏运行。并非每张图片都必须执行所有加工，也不能把普通缩放、叠字或图标替换冒充完整的原创美术生成。

## 3. 修改现有游戏的默认规则

### 3.1 默认保留

用户没有要求改美术时，已有角色外观、场景、卡面、配色、画风、构图和视觉身份默认保持原样。应直接复用现有素材，而非重新调用生成模型后期待它“画得差不多”。

“重新制作这个游戏”“重新打包”“重试失败步骤”或“修改后生成新版本”均不自动表示用户要求重画美术。明确要求重新设计外观、重画素材或更换整体风格时，才进入相应视觉更新。

### 3.2 按修改范围处理

| 用户要求 | 默认处理 |
| --- | --- |
| 攻击伤害从10改成15 | 更新规则和数值；保留角色、场景、卡面图片 |
| 调整胜利条件、难度或敌人波次 | 修改对应逻辑；保留现有素材 |
| 修改名字、口头禅、说明文字 | 更新相关文字显示；保留插画本身 |
| 新增一个人物或一张卡 | 生成新增对象需要的美术；已有对象保持不变 |
| 把某个人物的衣服改为红色 | 局部修改该人物及确有必要的同一人物衍生素材；保留未提及的脸、姿态、背景和其他人物 |
| 把场景从白天改为夜晚 | 更新指定场景的光照与氛围；保留人物及未要求改变的场景结构 |
| 重画一张卡面 | 只更新该卡面及必要的运行衍生文件；其他卡面保持不变 |
| 更换整款游戏的美术风格 | 可更新用户明确纳入范围的全局美术，并保留原版本 |

若玩法修改可能影响视觉表现，但用户未明确要求改图，系统应先复用现有美术。确实无法兼容时，说明具体受影响的素材与原因，再由用户决定是否更新；不得静默扩大修改范围。

### 3.3 技术加工与重画的区别

为适配运行环境而重新导出尺寸、压缩格式或整理纹理，可以生成新的技术衍生文件，但应保留原图和视觉内容，不得借加工改变人物长相、画风或场景构图。

未受影响的素材应保持同一文件或同一内容哈希。需要局部更新的素材，应以旧图和已确认约束为编辑依据，尽量锁定其他部分。

## 4. 素材与版本记录

每项素材应有稳定标识，并区分：用户参考输入、生成原图、加工衍生图及游戏中使用的成品。

素材记录至少能够追踪：

- 对应游戏、人物、场景或卡牌的稳定标识。
- 素材版本及来源，所属游戏方案或生成任务版本。
- 生成或编辑依据、输入参考、保留约束和加工关系。
- 原始内容与成品的内容哈希或其他等效身份依据。
- 当前游戏版本实际使用的素材版本。

修改游戏逻辑不能直接清空整套美术或解绑所有素材。是否更新由本次明确的修改范围决定。

替换素材应产生新版本，原版本保留并可追溯。某张图生成失败时，只重试失败或受影响的步骤；不得连带重新生成已经成功且无须改动的素材。失败结果不能覆盖现有可用版本。

## 5. 网站交互与完成状态

制作过程中应显示实际进展，例如方案处理、美术生成、素材加工、游戏组装及运行验证；不能用虚假的固定进度假装各步骤已完成。

修改时应展示简明摘要：哪些规则变化、哪些素材继续复用、哪些素材需要新增或局部修改。普通数值修改不应要求用户逐张重新确认全部图片。

图片生成服务不可用或尚未接入时，网站必须明确提示未完成美术生成。可以保留草稿或显示标明用途的开发预览，不能把它标为满足本要求的最终游戏。

游戏必须实际加载并使用本次制作所绑定的美术；只有图库、设定图或文字规则说明，不构成最终交付。

## 6. 验收条件

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| ART-01 | 制作一款新游戏 | 按本次设定执行所需美术生成、加工和运行绑定，而非统一套用演示图 |
| ART-02 | 完成制作 | 交付可玩的图形游戏，所需成品素材已被实际加载 |
| ART-03 | 仅修改伤害、难度或胜负条件 | 原有美术内容哈希或等效身份保持一致，不重新生成 |
| ART-04 | 仅修改一个角色的外观 | 只更新该角色及明确受影响的衍生素材，其他角色和场景保持一致 |
| ART-05 | 新增角色或卡牌 | 只新增所需美术，已有素材保持一致 |
| ART-06 | 某张图生成失败后重试 | 保留其他成功素材；只重试失败或受影响步骤 |
| ART-07 | 为运行需要重新导出图片 | 原图保留，技术衍生文件不改变已确认视觉内容 |
| ART-08 | 未接入图片模型 | 明示能力缺口，不能把文字、图标或开发占位素材当作完成 |
| ART-09 | 查看或恢复旧版本 | 能定位原版本的游戏配置和素材关系，不被新素材静默覆盖 |
| ART-10 | 修改范围可能影响美术但用户未要求改图 | 优先复用；确有兼容问题时说明并由用户决定是否更新 |

## 7. 实现边界

用户此前选择先完成本地模板版、稍后接模型，这一开发顺序不取消本文的最终产品要求。当前规则原型和美术需求清单只是开发基础；网站自动生成新美术、加工、局部编辑及稳定复用仍须实现和验证。

模型提供方、预算、生成耗时和具体加工工具另行确定。不能把对话中一次性调用图片工具等同于网站已具备运行时图片生成服务。
