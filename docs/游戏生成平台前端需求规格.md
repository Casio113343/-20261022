# 多类型游戏生成平台：前端需求规格

- 日期：2026-10-31
- 状态：已确认需求基线；实现进度以各阶段验证记录为准。
- 依据：本轮用户确认的自然语言需求。本文是项目需求整理，不是课程原文。

## 1. 产品定位与范围

平台引导用户指定游戏类型、参考玩法和原创素材，由系统补充设计，形成可试玩、可继续修改的游戏。支持方向包含 MOBA、RPG、塔防、卡牌等，不限定为互动小说或单一卡牌游戏。

本项目为多类型游戏生成平台。技术栈、函数式编程标准及两个案例的工程架构约束继续适用。游戏生成模块、运行引擎和后端接口须另行设计。

本规格定义创作入口、信息收集和生成前确认。具体视觉稿、完整页面数量、生成引擎及各类型首版可玩范围尚未确定。

### 1.1 图像产物硬性要求（2026-10-31用户新增）

- 本平台必须生成实际图像、图片内容，不能以文字游戏作为最终作品形式。
- 文字介绍、需求表单和设计方案可用于创作引导，但单独提供文字叙事、聊天选项、规则说明或数值面板，不算完成游戏生成。
- 用户上传的参考图片属于输入素材，不能冒充系统已经生成的美术产物。
- 当前本地模板原型使用基础图形与图标，尚未接入根据用户设定创作角色、场景或卡面的图片生成能力，不能据此宣称已满足本条。
- 用户已确认最终交付为可玩的图形游戏及配套美术；每次新的游戏制作请求必须根据本次设定生成所需角色、场景、卡面等图片，并加工、绑定到游戏运行中。
- 修改已有游戏时默认复用美术，除用户明确提及的视觉变化及必要的局部配套加工外，其余美术尽量保持不变；普通数值、规则或文字修改不得触发整套美术重画。
- 详细生成流程、局部修改、稳定复用和验收条件以 [游戏生成与美术保留规则](./游戏生成与美术保留规则.md) 为准。本条优先于旧的简化模板验收口径。

## 2. 规范用语

- 必须：实现及验收不可缺失。
- 应：默认执行的交互设计，调整时应说明理由。
- 待确定：尚未批准的实现参数，不得当作已经完成的功能。

## 3. 用户流程与页面区域

主流程：浏览分类和介绍 → 选择玩法 → 填写参考玩法与创作要求 → 补充世界观及人物 → 整理并修改方案 → 确认制作 → 生成美术并加工 → 组装和验证可玩的图形游戏 → 试玩与局部修改。

创作入口必须呈现四个可辨识区域：游戏分类与要求、世界观、人物、生成前方案预览。世界观和人物位于玩法要求之后。具体采用单页分区还是步骤式布局待视觉设计确定；返回编辑不得清空已输入内容。

## 4. 游戏分类与介绍

### 4.1 分类原则

采用市场常见名称组织“大类＋具体玩法”，帮助普通用户理解。市场分类存在交叉，本文目录是产品入口初稿，不宣称唯一行业标准。参考 Steam 的游戏类型与玩法标签：https://store.steampowered.com/search/?category2=7 。分类参考日期为 2026-10-31。

| 大类 | 具体玩法示例 | 介绍重点 |
| --- | --- | --- |
| 动作与对战 | MOBA、格斗、射击、动作闯关 | 控制角色移动和攻击，通过操作与战术完成对抗 |
| 角色扮演 RPG | 回合制、动作 RPG、小队冒险 | 扮演角色探索，通过任务、战斗和装备成长 |
| 策略 | 塔防、即时战略、回合策略、自走棋 | 配置资源、阵容或建筑，通过决策达成目标 |
| 卡牌与桌面 | 卡牌对战、牌组构筑、身份对抗 | 运用卡牌效果、时机与角色能力展开博弈 |
| 模拟与经营 | 商店经营、城市建设、生活模拟 | 管理持续运转的场所或系统并逐步发展 |
| 探索与解谜 | 密室、机关解谜、生存探索 | 观察环境、收集线索或资源并解决问题 |

目录必须覆盖已讨论的 MOBA、RPG、塔防、卡牌方向。其余条目作为分类扩展基线；目录出现某类型不代表生成能力已实现。每项必须显示实际支持状态与可生成范围；暂不支持的类型可以查看介绍，但不得伪装为可生成。

### 4.2 门类详情

每个具体门类必须提供独立的介绍与要求输入区域。切换门类后介绍及提示随之变化。

介绍必须说明：玩家控制的对象、核心操作、典型流程、常见胜负或完成条件、常见机制及当前支持范围。不得只给缩写或一句宣传语。

创作要求输入框用于自然语言描述希望加入、改变、删除的机制。提示必须贴合所选类型。例如 MOBA 提示队伍规模、推塔、兵线、野区；塔防提示路线、波次、建塔与升级。提示是帮助，不要求用户逐项填写。

### 4.3 玩法字段

| 字段 | 要求 | 规则 |
| --- | --- | --- |
| 主要游戏类型与具体玩法 | 必填 | 必须明确本次生成的主要玩法；组合方式待细化 |
| 参考游戏或参考模式 | 必填 | 明确“类似什么”；不得只有“好玩”等抽象描述 |
| 希望保留的参考机制 | 应提供 | 系统可根据参考内容提出草案，由用户确认，不能默认为完整复刻 |
| 自定义创作要求 | 必须提供输入框，内容可选 | 接受自然语言；未知部分允许系统补充 |

示例：“卡牌策略，参考三国杀的身份对抗模式，希望保留隐藏身份和轮流出牌；角色资料见下方。”仅填写参考游戏名称时，系统应在预览中明确采用的模式和机制，供用户修改。

## 5. 世界观区域

必须提供世界观文字输入及参考图片入口，支持直接粘贴已有设定。以下内容作为可选填写引导，不强制用户拆分已有文字。

| 信息 | 示例 |
| --- | --- |
| 世界背景 | 漂浮在云海上的城市 |
| 阵营与冲突 | 天空居民与地表来客争夺能源 |
| 特殊规则 | 使用魔法会消耗记忆 |
| 场景与视觉 | 废弃车站、巨大风车、明亮手绘风格 |
| 必须保留的设定 | 世界没有传统意义上的反派 |
| 允许系统补充的范围 | 城市名称、支线地点、普通敌人 |

世界观可留空，留空表示尚未提供，不等同于用户已确认系统生成的设定。图片应支持多张，并可标注“建筑参考”“地图草图”等用途。上传不表示系统已经完成图片理解，失败或不支持时必须明确反馈。

## 6. 人物区域

必须以可新增、编辑、删除的角色卡组织多个人物，每张卡独立承载以下已知信息：

| 字段 | 规则 |
| --- | --- |
| 图片 | 可选，可添加用途说明 |
| 名字 | 支持填写；暂缺时用界面序号识别，不冒充正式命名 |
| 身份、阵营、背景经历 | 可选文字 |
| 已知性格 | 可选文字，作为角色设计依据 |
| 口头禅、说话方式 | 可选文字，保留用户原意 |
| 人物关系 | 可选，可描述与其他角色的关系 |
| 想要的技能、武器、特殊能力 | 可用自然语言表达，无须填写数值公式 |
| 玩法定位 | 可选，例如输出、辅助、防守 |
| 必须保留的特点 | 系统补充时必须遵守 |
| 允许系统补充的范围 | 标明哪些内容可以自由设计 |

人物信息允许不完整，也允许暂不添加人物。系统应把性格和技能设想转为符合所选玩法的设计，并在方案中展示补充的效果、条件、消耗与限制。

切换游戏类型必须保留世界观、人物原始资料与图片。已补充的技能规则应标记需要重新适配；不得静默删除资料或声称旧规则已适用于新玩法。有内容的角色卡删除应提供确认或撤销能力。

## 7. 方案预览与生成

“整理我的游戏方案”必须基于当前填写内容生成可审阅方案，至少包含：游戏类型、参考模式与采用机制、核心流程、世界观、人物与技能、胜负或完成条件、系统补充项、尚未解决的问题。

必须明确区分“用户提供或已确认”与“系统建议补充”。用户可以修改方案并返回相应输入区域。系统不得将生成建议冒充用户原始要求；违反用户必须保留的内容或存在明显矛盾时，应指出冲突并请求调整。

预览后由用户确认再启动游戏生成。生成必须使用用户确认的方案版本；确认后修改输入，旧方案应标记待更新，不能拿过期方案静默生成。

最终目标是提供使用本次生成美术的可玩图形游戏，并支持以自然语言提出修改要求。文字方案、静态图库或通用演示图不算最终游戏完成。修改必须遵循 [美术保留规则](./游戏生成与美术保留规则.md)，不能因重建游戏逻辑而清空或重画全部素材。具体页面布局另行设计；本文不宣称已具备相关能力。

## 8. 输入、上传与操作反馈

- 必填校验必须识别空白输入，在对应区域显示原因并可定位；不得清空其他内容。
- 世界观、人物可不完整，不得通过大量必答问题阻塞提交。
- 图片必须有预览、移除和上传状态；上传失败允许重试并保留其他资料。
- 文件格式、体积、数量和文本长度限制须在实施前确定，前后端一致，并在操作前告知。
- 方案整理及游戏生成必须区分处理中、成功、失败；处理中防止重复提交，失败保留草稿并提供重试。
- 本次编辑会话中的内容必须在分区切换和预览返回时保留；刷新后恢复、跨设备保存及登录要求待确定。
- 输入框必须有可见标签；错误、选中及上传状态不得仅依赖颜色，主要操作可通过键盘完成。

## 9. 前端工程约束

继续使用 TypeScript、React、Tailwind，按项目编码规章组织页面骨架、页面 Hook、纯函数、类型及业务区域组件。业务核心采用不可变数据与纯函数；网络、上传、存储和 UI 状态更新位于显式副作用边界。Zustand 仅按跨页共享需要使用。

本文不指定生成引擎、后端领域模块、接口签名或存储方案。设计说明、规则预览和真正可玩的产物必须在界面上清楚区分。

## 10. 验收条件

| 编号 | 场景与预期 |
| --- | --- |
| FE-01 | 用户可查看分类、具体玩法和完整介绍，清楚知道支持范围 |
| FE-02 | 每个具体门类有对应要求框和匹配的提示 |
| FE-03 | 未填写参考游戏或模式时不能进入方案整理，并定位错误 |
| FE-04 | 仅提供玩法和参考模式、未填世界观及人物时，允许整理补充方案 |
| FE-05 | 可填写世界观、添加参考图并标注用途；上传失败可重试 |
| FE-06 | 可维护多张角色卡，填写名字、性格、口头禅和技能设想等资料 |
| FE-07 | 切换类型不丢原始素材，旧技能设计提示重新适配 |
| FE-08 | 预览区分用户资料和系统补充，支持修改及返回编辑 |
| FE-09 | 修改确认依据后不能静默使用旧方案生成；实际生成需用户确认 |
| FE-10 | 处理失败不丢草稿，重复点击不产生重复操作 |
| FE-11 | 不支持的类型不会被显示为已具备生成能力 |
| FE-12 | 创作入口按分类、玩法要求、世界观、人物和方案确认组织完整流程 |
| FE-13 | 最终作品包含实际生成的图像/图片；文字游戏、纯说明或纯数值面板不能作为完成结果 |
| FE-14 | 输入参考图与系统生成图清楚区分；未接入图片生成时明确标示能力缺口 |
| FE-15 | 每次新游戏制作都按本次设定生成、加工所需美术，并用于实际可玩的游戏 |
| FE-16 | 普通规则或数值修改保持已有美术一致；仅对明确提及的视觉变化局部更新 |
| FE-17 | 修改摘要区分复用、新增和局部更新的素材，失败重试不重画无关素材 |

上述为后续实现的验收标准，本次仅完成文档核验，不表示功能已经通过验收。

## 11. 待确定事项

1. 首批真正可生成的类型、各类型规模及单机或联网边界。
2. 分类完整目录、组合玩法选择方式与介绍文案。
3. 图片与文本限制、图片理解能力、素材存储规则。
4. 登录、持久草稿、作品管理、版本回退与分享范围。
5. 生成引擎、资源制作方式、运行环境、耗时和预算。
6. 视觉风格、响应式布局与最终页面清单。
